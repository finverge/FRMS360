What changed since v1.0

v1.0 described a platform with no authentication layer worth the name, no way to file a return, and eight detection indicators inert for want of data feeds. All three have been closed. This revision rewrites identity and access (§13) and data protection (§14) from scratch, adds regulatory artefacts (§10), backfill, replay and simulation (§8) and a seventh service, and restates the gap register against the R1–R5 release gates in BRD v1.10. Sections whose design has not changed are unchanged.

Why the rail adapters sit at the edge and not in the rules

A UPI collect request, an IMPS P2A transfer and a card authorisation describe the same event with different field names, different amount units and different notions of who initiated it. If that variation reaches the rule engine, every indicator has to know about every rail, and adding a sixth rail means editing thirty-three indicators. Normalising once at intake means a rail is an adapter, and the detection code has never heard of UPI.

Why detection lives inside analytics-service

Detection writes the facts that analytics reads, and case management mutates them. Splitting them today would mean one service writing another's tables — the shared-database problem, made worse. The cases schema is already separated so the eventual split is a deployment change rather than an excavation, but it is blocked on a real trade: an event-synced read model would break the exact reconciliation P1 depends on. That decision is open (BRD OD-02).

How every service decides what a role may do: the tenant's own rows, and nothing in code

What a role may do is data. A tenant's roles are rows in tenant.tenant_roles — modules, dashboards, three capability flags and a list of permissions (the gated actions in cp_common.permissions) — seeded from the starter templates in cp_common.rbac at onboarding and edited by the tenant's administrators from then on. tenant-service reads them directly. Every other service that authorises a human request — analytics, config, decision (review), notification and lane-c — has no grant on that schema (schema-per-service, AD-03), so each asks cp_common.dynamic_roles, a shared module written once, which fetches the tenant's rows over HTTP from GET /tenants/internal/{tenant_id}/roles and caches them against the "roles" generation on the mechanism (cp_common.cache) that config-service already bumps for rule and policy changes. A role edit is therefore live in every service on the next request, not after a TTL. There is no in-process catalogue to answer from, no list of role names in any endpoint and no implicit administrator override; has_permission(tenant, role, permission) is the single question an endpoint asks.

Failure behaviour is fail-closed by design. A role name that is not one of the tenant's rows can do nothing. If tenant-service cannot be reached, a service keeps serving the last copy it cached and retries; one that has never cached the tenant's roles refuses the request. A failed fetch is never stored as "this tenant has no roles", which would turn one network blip into a lasting lock-out. This is a deliberately different trade from decision-service's own catalogue_for() (Lane A, below), which may never block and so serves a stale copy while refreshing: authorisation is not on the payment path, and refusing for a moment is better than honouring a grant an administrator has just withdrawn. The cost is that tenant-service is on the authorisation path of every service, which is why deployment runs it on two app VMs behind the internal listener and monitors its readiness. ingestion-service has no human role checks (BR-213 machine credentials carry scopes), and the /decide path does not consult roles at all.

Guard-rails that remain are in tenant-service's write path, not in the services that read: unknown permissions, the platform-only module and Tenant Health are refused; raising a capability flag or adding a permission is staged for a second person (pending_change) while lowering applies at once; an edit or delete that would leave a tenant with no working administrator, or delete a role someone holds, is refused; every change writes a before/after snapshot to the audit trail. The one role outside the table is the platform operator (platform_admin), recognised by name because it is not a bank's role.

config-service: the rule catalogue is no longer identical for every tenant (BR-111)

Onboarding used to seed the same EWS catalogue regardless of entity type — only the FRM policy body was entity-type aware. ENTITY_TYPES now carries a can_extend_credit flag per entity type, checked against each of the nine RBI 2026 Directions' own Chapter III text rather than assumed, and rule_configs() accepts it to drop the 20 rules whose premise is a lending relationship (loan-account misuse, borrowal-account conduct, collateral, title disputes, related-party exposure, qualitative credit signals, loan origination — BR-214) for an entity type that cannot extend credit — today, only Payments Bank. This is capability-gated seeding, not a per-tenant override: it happens once, at onboarding, in default_configs_for(), and what gets seeded is what internal_active_rules serves to decision-service and analytics-service — an excluded rule is absent from the tenant's configuration, not merely deactivated. Trade- finance rules (TBM) are deliberately not gated the same way: none of the nine Directions tie Authorised Dealer / forex authorisation to entity type, so that would need a new per-tenant signal the platform does not capture yet, not an entity-type default. See FSD §"Detection scope" for the functional detail and BRD BR-111 for the traceable requirement.

Not yet built: Central Fraud Registry reporting (BR-509)

Each of the nine 2026 Directions carries its own Chapter VI sub-section on reporting to RBI's Central Fraud Registry (CFR), distinct from the FMR return BR-504/505 already covers. Nothing in this codebase names CFR today. The expected shape is an extension of the same filing-artefact-to-prescribed-format binding BR-504/505 already tracks as not_bound pending OD-04 — not a new cross-tenant data-sharing mechanism. That distinction matters: the tenant-isolation boundary this section treats as inviolable elsewhere (an unscoped key is a cross-tenant leak waiting to happen) is not to be weakened to build this — each tenant reports its own incidents to RBI's registry, the same way it already reports FMR/STR, not into a database shared across tenants. Not built; timing not yet committed (BRD BR-509).

A control total that only fails part of a file is not a control total

ISO 20022 carries its own count and sum in the group header. The obvious implementation rejects the rows that disagree and keeps the rest — which is precisely wrong. If the declared sum does not match the parsed sum, the disagreement is about what the file contains; there is no basis for deciding which rows are the good ones. The file is refused whole and the bank is told the declared and computed figures. Partial acceptance under a failed control total is how two systems end up holding different versions of the same day.

Rows that fail validation are written to quarantined_rows with their reason rather than dropped. "We sent you 40,000 rows and you booked 39,997" is a question the platform has to be able to answer with the three rows, not with a count.

A fifth channel not yet built: loan-origination (LOS) signals (BR-214)

All four channels above are post-disbursement — even CBS loan-conduct events start at sanction, not at application. ~92% of FY25 reported bank fraud value is loan/advances fraud (RBI Annual Report FY25), and a falsified application or a straw borrower is invisible to this platform until money has already moved. A fifth channel reading the underwriting/LOS stage would extend the same canonical-shape-at-the-edge pattern this section already uses, not require a new architecture - but LOS systems vary far more across NBFCs and co-operative banks than core banking does, so the adapter surface is larger than the four above. Not built; timing not yet committed (BRD BR-214).

Observations are computed per account, once per batch, rather than per transaction — a handful of aggregate queries instead of one query per row. An unloaded list is not a clean screen

CPT-02 screens counterparties against a sanctions list. If no list has been loaded, the tempting implementation returns "no match" — and a bank reads that as screened, clean. It reports the indicator as unmeasurable, with the reason, and the case surfaces say so. The same rule governs every dependent indicator: a proportion whose denominator is absent is omitted, never returned as zero. Loading an empty list is refused outright, and a feed that arrives materially smaller than the version it would replace is refused with the previous version left active — a truncated sanctions file is indistinguishable from a clean one at the moment it is applied, and only distinguishable afterwards by the frauds that were not flagged.

Comparator direction is part of the configuration

Most indicators fire at or above their threshold. "Beneficiary added within 24 hours" cannot be expressed that way — a two-hour-old payee is more suspicious than a twenty-hour-old one. Each rule therefore carries an explicit comparator. Without it the two age-based indicators compared the wrong way round and never fired at all: a silently dormant fraud indicator, which is exactly the finding an inspection looks for.

Inline decisioning — Lane A

A go/no-go answer inside the payment window, without pretending the near-real-time lane can be made to fit in one.

The detection runtime above drains a queue. It sees a transaction after it has been ingested, scores it against the full catalogue with complete account context, and raises an alert. That is the right design for an early-warning system and the wrong design for a UPI authorisation, which must be answered in a few hundred milliseconds end to end. Stretching one lane to cover both would have meant either a detection engine that skips work it should do, or a payment that waits for work it should not.

Which rules can go inline is a property of the rule, not a preference

A rule is inline-eligible only if it can be answered from precomputed per-account counters or from what the channel already sends. The other 19 are listed with the reason each is excluded — a graph traversal whose cycle has not closed, a reference-list join, a CBS event posted after settlement. That register is code (inline_rules.py), keyed by rule id, so a new rule has to declare which lane it belongs to before it can be catalogued.

Two exclusions are about correctness rather than latency. CPT-01 and VEL-02 measure beneficiary age with an lte comparator, and the first-seen-pair set they need is not an account counter. Scored from a context without it, an unknown payee reads as age zero — and the rule fires on every high-value payment. A control that declines everything is as broken as one that declines nothing, so they are suppressed explicitly and reported unmeasured.

One definition per figure, across both lanes

Lane A and Lane B share cp_common.observations.observe(). They do not each have their own idea of what "velocity" means. If the two lanes could drift apart on a definition, a tenant would eventually see an inline decline and a Lane B dashboard that disagreed about the same account, and there would be no way to say which was right.

An action the rail cannot execute is worse than no action

The action set is a property of the payment scheme, not a tenant preference, and it is checked when the policy is configured rather than when the payment arrives. On UPI the PIN is captured at the remitter PSP before the request reaches the bank, so the customer has already authenticated and the NPCI response set is approve or decline — there is no step-up code to return. IMPS is the same. Card is the exception: 3-D Secure makes a challenge a first-class protocol outcome. hold belongs only to NEFT and RTGS, which settle in a window wide enough for outward-remittance screening to be a real operation.

This was a live defect, not a hypothetical. The shipped starter policy offered challenge on UPI and made IMPS challenge-only — so that lane could never decline anything at all. Had a tenant enforced it, the decision log would have recorded a control firing, the switch would have ignored an answer it did not recognise, and the payment would have settled. Every report would have shown the control working. A rail with no declared capabilities is refused rather than assumed permissive, so a new scheme cannot inherit the most powerful set by default.

A second front door onto the same core: ISO 8583 (BR-317, Partial)

/decide above is JSON, reached directly at the decision-service host. Some card/EFT switches — frequently on-prem, vendor-licensed, no REST layer available without a change request per bank — have no practical way to originate that call. Asking each such vendor to build a translation layer of their own does not scale: it is N bespoke integration projects on infrastructure Fraud360 does not control, instead of one adapter built and tested once.

iso8583_gateway is that one adapter: a TCP listener, its own deployable for the same reason decision-service already is — a raw-socket connection has a different failure mode than an HTTP service behind the gateway, and a hung 8583 connection must not affect the JSON path or vice versa. It decodes an authorisation message (MTI 0100/0120), maps the standard data elements to a DecideIn body, and calls POST /decide exactly as any JSON integrator would — same rule catalogue, same per-rail policy, same decision log. Two front doors, one brain, deliberately: there is exactly one function in the platform that ever produces a decision, and this gateway is a client of it, not a second implementation of it.

What is built, and what is deliberately still open

The codec, field mapper and connection handler are complete and unit-tested (45 tests): message round-trip including LLVAR fields and leading-zero-preserving fixed fields, the DE7 year inference including the year-boundary case, PAN masking, and every failure path — a malformed message, an unreachable /decide, a /decide response this gateway cannot represent — producing an explicit refusal (DE39 96/91) rather than a guessed approval. iso8583_fail_open has no default, by the same discipline RailPolicy.fail already applies to every inline rail: the process refuses to start rather than pick open or closed on the bank's behalf.

Not built, and not guessable: DE48/62/120–127 are private-use in the 1987 standard and every switch vendor fills them differently, so this gateway maps only the public data elements until a named pilot vendor's own spec confirms the rest — see docs/ISO8583_LANE_A_SCOPING.md. Whether terminating a raw PAN here brings Fraud360 into PCI-DSS cardholder-data scope is a compliance decision, not an engineering one, and is likewise still open. Not deployed for any tenant.

Shadow mode

Every rail ships with shadow = true. The service computes the decision, records what it would have returned, and returns allow. A tenant can therefore run Lane A against real traffic for as long as it likes and measure the false-positive cost of enforcement before anyone's payment is declined. Turning enforcement on is a per-rail configuration change with a board-approval trail, not a deployment.

A rail with no inline policy is refused, not allowed. Answering "allow" for an unconfigured rail would make it look screened; a 409 makes the omission visible. The same applies to a rail explicitly configured for Lane B — asking Lane A about it is a configuration error, and it is reported as one.

The decision log is written after the answer is formed, and a failed write is swallowed deliberately. Losing a log line is bad; making a payment wait on our disk is worse. That is the one place in the platform where absence is not reported to the caller, and it is a considered trade rather than an oversight.

Backfill, replay and simulation

Retuning a threshold is worthless if nobody can see what it would have done. One code path answers all three questions.

Simulation is the same engine with the write suppressed and the candidate threshold substituted for the active one, so the answer it gives is the answer activation would produce. A separate estimator would be a second implementation of the rule semantics, and the first time the two disagreed nobody would know which was right.

A window's worth of context cannot measure a window

Backfill originally built one account context at the end of the requested range and scored every transaction against it. For a single-day run that is correct and it passed. Over a multi-day range it is not: a 24-hour aggregate computed at the range end describes the last day, so LAY-01, LAY-02 and VEL-03 — every rule with a 24-hour window — could not fire on any earlier day. Worse, because the counts were computed from the wrong baseline, threshold overrides had no observable effect at all: the simulation returned nearly the same answer whatever number was supplied, which is the most misleading possible behaviour for a feature whose entire purpose is to show the difference a threshold makes.

The run is now sliced per day and a fresh context is built for each. Verified by sweeping the threshold: LAY-02 returns 236 hits at the previous behaviour, 2,185 at a threshold of 2, and 0 at 106 — and a simulate run still writes zero alerts. A monotonic response to the parameter is the property that was missing, and it is now asserted by test.

Regulatory artefacts

Three things leave the building: the FMR return, the STR, and the board or ACB pack. All three are assembled from the metric registry, so none can disagree with the console.

Assembly, validation and refusal

A return is built from the case, its evidence, the reasoned order and the accountability findings. It is validated against a declared field schema, hashed, and retained with the hash so that "what did we file, and when" is answerable years later without trusting the current state of the case.

A return with gaps is refused rather than generated with blanks. A half-filled statutory form that looks complete is worse than no form: someone signs it. The refusal names the missing fields, which is also the fastest route to a complete one.

The format binding is declared, and it is declared not_bound

The platform assembles, validates, hashes and retains the return, and a named officer can submit from the pack. What it does not claim is that the file is in RBI's or FIU-IND's prescribed format — because the prescribed schemas have not been supplied. Rather than quietly emitting a plausible-looking CSV, the format binding is an explicit field whose value is not_bound, and it is visible on the artefact. This is the single blocker on release gate R2 (BRD BR-504/505, open decision OD-04). It needs the published schemas, not engineering.

The STR path itself is now verified end-to-end, not merely designed: a defect left the Principal Officer field — mandatory on every STR under PMLA Rule 7 — with no source anywhere in the platform, so generation was refused for every case regardless of format binding. The field now reads from the tenant's board-attested FRM policy (rides the same board_approved / attestation mechanism as every other governance fact in that policy, rather than a separate approval path invented for it) and has been confirmed against a live case through the real API. A tenant admin can now set that field themselves: ConfigCreate.kind was refusing policy at the request schema, blocking the console and the API both; that is fixed, and creating a new policy version still requires the same board attestation to activate as every other policy fact.

Board and ACB pack

Scheduled, versioned, and rendered from the same metric definitions the board sees on screen — the pack cannot become a separately maintained set of numbers. Distribution is recorded per recipient, so "who received the September pack" is a query rather than an email search.

Referral and recovery

Law-enforcement referrals and recovery entries hang off the case. Recovery re-derives the case's recovered total under a row lock rather than incrementing a counter, and a recovery that would exceed the loss is refused. write_off is deliberately absent from the recovery vocabulary: writing off a fraud loss is an accounting decision, and recording it as recovery would flatter the one figure a board is most likely to quote.

Reconciliation by construction

How P1 is actually achieved, and how it is proven at query time.

A central registry defines each metric once — its SQL expression, its base entity, its unit and its filter semantics. Dashboards do not write SQL; they name metrics. Two surfaces showing "fraud value" are therefore reading the same definition, and cannot drift apart.

Sixteen invariants run at query time and are displayed beside the figures. Integrity checks run tenant-wide; consistency checks run under whatever filters the user has applied, so the assurance matches the view being looked at.

An invariant that was wrong for months

R-03 asserts a case's value equals the value of its underlying transactions. It joined case → alert → transaction, counting a transaction once per alert. That passed only because the synthetic generator emitted exactly one alert per transaction. Live detection fires every matching rule, so a ₹9.87 lakh payment tripping five rules appeared as ₹49.3 lakh of evidence and seven cases failed immediately. The engine was right; the check was wrong. It now sums distinct transactions. The same flaw existed in the per-case evidence panel.

Worth recording as a design lesson: an invariant validated only against generated data is validated against that generator's assumptions, not against reality.

Signature wrapping is the SAML failure that matters

The classic SAML break is not a forged signature — it is a valid signature over a document element that is not the one the code goes on to read. An attacker keeps the genuine signed assertion, wraps it, and adds their own unsigned assertion elsewhere in the tree; naïve verification passes, and the application then reads the attacker's element.

The implementation therefore reads the subject and attributes from the element the signature actually covers, rather than verifying and then re-querying the document. Exclusive canonicalisation is delegated to a maintained library rather than hand-rolled — canonicalisation bugs are silent and produce a validator that accepts documents it should not. Assertion IDs already seen are recorded and refused, so a captured assertion cannot be replayed.

Why a payment switch is not a user with MFA disabled

A switch, a CBS extract job and an ETL pipeline all have to call intake, and none of them can complete a TOTP challenge. The tempting fix is to exempt one user account. That is wrong twice: it creates a human-shaped account whose second factor is off — a switch someone eventually flips on a real person — and it attributes every ingested batch to whichever employee's password went into the switch's config.

MFA exists because secrets leak, so removing it has to be paid for rather than simply dropped. What replaces it here is scope (a stolen intake key cannot read a case, a customer or a dashboard), certificate binding (possession, where the bank can offer mTLS), an address allow-list, and expiry with overlapping rotation. Where the bank terminates TLS at its own edge and forwards the thumbprint in a header, the credential records that it proves trust in the edge rather than possession — the two must never read as equivalent in an IS review.

The standard principal dependency refuses machine tokens by default. Endpoints opt in. Defaulting the other way would silently expose every new endpoint until someone remembered to close it.

Tenant lifecycle as an access control

Suspension used to gate the console login and nothing else: a suspended bank's staff were locked out while its payment switch kept posting and its channel kept asking for inline decisions. That is the wrong half — the machine path carries the volume and the billing. The lifecycle check now sits on the single dependency every machine caller passes through, so intake and decisioning are both covered, and a new machine endpoint inherits it.

Intake and decision services have no grant on the tenant register, so standing is fetched over the internal API and cached for 15 seconds — a switch at thousands of transactions a second cannot take a cross-service hop per call. The cost is stated rather than hidden: a suspension bites within that window, not instantly. If tenant-service is unreachable the last known answer is used and marked stale; if nothing was ever known the tenant is served, because a tenant-service outage must not become a payments outage. That is the one deliberate fail-open in the platform, and it is recorded on the result so it can be audited rather than assumed.

A suspended tenant can still export. The refusal message says so, because the bank's first question on being suspended is whether its data is gone.

Privacy of customer data

Customer identifiers are masked server-side by default — masking happens before the data leaves the service, not in the browser. Unmasking requires both a role capability and a recorded justification, and the act of viewing customer-level evidence is itself audited, not merely changes to it.

Capability is withheld from aggregate-only roles (board, CRO), from model work, and from platform staff. Operating the service does not require seeing a bank's customers, and an outsourcing review asks that question first.

Console output encoding

Every value interpolated into markup in the console is escaped at the point of interpolation. This was not originally true: an analyst's typed disposition reason reached the DOM unescaped, which is stored cross-site scripting in a screen shown to supervisors and, in the board module, to directors. A checker walks every markup-bearing template literal and fails the build on an unescaped interpolation, with each of the handful of exemptions carrying a written reason. Style guidance would not have held; roughly 190 call sites needed fixing.

Data protection and retention

Two obligations that pull in opposite directions — DPDP says delete, RBI says keep — resolved by making the floors non-negotiable.

Secrets at rest

MFA seeds, identity-provider client secrets and reference-feed credentials are sealed with AES-256-GCM under a versioned key. The record's identity is bound in as additional authenticated data, so a ciphertext lifted from one row and pasted into another fails to open rather than silently decrypting into the wrong context. Sealing is a column type rather than call sites, so a new secret column cannot be added unsealed by omission, and re-sealing an already-sealed value is a no-op so a re-run cannot double-wrap. With no key configured, writing a secret raises rather than storing plaintext.

What this does not cover is the volume itself. Full-disk or tablespace encryption protects a stolen disk or a discarded backup and is a deployment control — Postgres TDE, LUKS, or the cloud provider's volume encryption. An IS review asks for both layers; this is the outstanding half of BRD BR-712.

Exit — what the bank takes with it

The outsourcing directions require data return in a usable format when the relationship ends. The bundle used to contain the tenant record, users, branding, thresholds and the audit trail — all real, but none of it the part a bank cannot rebuild. The fraud record is: cases, the alerts underneath them, the transactions those alerts were raised on, the transition log including refusals, the accountability examinations and findings, LEA referrals, recoveries, and the filed FMR/STR returns with their payloads and content hashes. Those carry statutory retention obligations that outlive the contract and exist nowhere else.

Two deliberate omissions, both counted rather than dropped. The full transaction history is not in the bundle — a tenant with thirty million rows does not want them in a JSON document, and pretending otherwise produces something nobody can open; the count is stated and the bulk CSV path is named. Document bytes are not in the bundle either; each appears in a manifest with its SHA-256, so what is downloaded separately can be verified against what we held.

A partial bundle must never look complete

The previous implementation swallowed a failed branding or configuration fetch and returned the bundle as though nothing were missing. On an exit export that is the worst place in the system for a silent gap, because the bank discovers it after the tenant is gone. Every section that fails is now recorded as null with the reason, and the bundle carries an explicit complete flag so a caller can tell a whole bundle from a partial one without inspecting every section. The flag earned itself immediately: it caught an unbound query parameter in the platform's own export on the first end-to-end run.

Reliability and scale

The platform is designed to run as several replicas of each service behind a load balancer. Three mechanisms make that safe.

Configuration coherence across replicas

Tenant configuration was cached per process with a time-to-live. With four replicas that meant the same dashboard, refreshed twice, could return two different sets of numbers depending on which replica served it — for a platform whose central claim is reconciliation, not staleness but wrongness.

Caching is now keyed to a shared generation token. Every replica reads the same counter; config-service bumps it on change; a replica whose cached copy predates the current generation discards it. The generation read is authoritative on every call — any non-zero backstop TTL simply reopens the same bug with a shorter window. A deployment configured with a process-local cache and more than one replica refuses to start.

Failure isolation at the edge

MechanismBehaviour
Circuit breaker, per upstreamAfter repeated failures, calls to that upstream fail immediately instead of occupying a connection for the full timeout. One probe is admitted after the cool-down — a thundering herd re-breaks a service at the moment it recovers
Split timeoutsConnect 2s, read 25s. A dead upstream does not deserve thirty seconds; a slow analytical query does
Bounded poolOne slow upstream cannot consume every connection the gateway has — the specific way a degraded service used to take the whole console down
RetryReads always; writes only when the caller supplied an idempotency key
Rate limitToken bucket per caller. In-process, so with N replicas the effective ceiling is N× — a safety valve against runaway clients, not a billing control

Measured with analytics-service stopped: the first call failed after retries, the breaker opened, subsequent calls returned in about ten milliseconds, and the tenant and audit endpoints continued serving normally throughout.

Idempotency

A write labelled with an Idempotency-Key is executed once; a retry replays the stored response. Three cases are distinguished rather than collapsed: same request already finished (replay), same request still running (409 — the first attempt may yet commit), and a different request under the same key (422 — a client bug that must not silently discard either request). Keys are scoped to the authenticated principal; an unscoped key is a cross-tenant leak waiting to happen.

Liveness versus readiness

Liveness deliberately does not touch the database. If it did, one brief database outage would fail liveness on every replica simultaneously and the orchestrator would restart the entire fleet — turning a dependency wobble into an outage. Readiness does check dependencies, returning 503 so the load balancer removes that replica from rotation.

Pipeline freshness is the gauge that matters. Request latency tells you the console is responsive; it says nothing about whether detection has fallen an hour behind. Five meters, aggregated per tenant per day and then marked final. A finalised day is never recomputed: an invoice that changes after it is issued is not an invoice. Seats are a high-water mark within the day rather than a sum — summing daily seat counts across a month bills a bank thirty times for the same analyst.

Tracing remains the notable absence. Correlation ids flow correctly across every service, but nothing collects them, so the cost has been paid and the benefit is not yet available.

Deployment architecture

Trust decreases upward: the data tier accepts no ingress from outside the private network, the application tier is unreachable except through the gateway, and only the edge is exposed. AI/ML roadmap — architecture

How the four phases this document's own AD-05 ("rules engine rather than ML — revisit when...") anticipates would actually be built, against the architecture as it stands today — not a restatement of the business case, which lives at BRD §19. None of this is built; each phase's design below only firms up once the phase before it lands.

Phase 1 — Device & behavioural biometrics

No new service. Ingestion-service's transaction payload already carries a device id (§5); this phase widens that same payload with a device-posture and behavioural-biometric feature vector, sourced from VideoPD / the Human Fraud Detection Framework rather than captured here, and adds new sub-rules to the channel/device (CHN) family the detection runtime already evaluates (§6) — CHN-01 and CHN-03 are measured from transactions alone today; the new sub-rules join them at the same evaluation step, not a separate one. No architectural decision is revisited: AD-05 (rules engine, not ML) still holds, because this phase adds signal inputs to the existing rules engine rather than a scored model.

Phase 2 — Transaction velocity & anomaly-detection models Built

The first phase that touches AD-05 directly, and the first one actually built. The model config kind and its champion/challenger gate (BR-807/808) were already built in config-service; this phase added the scoring side — a model-scoring step in the detection worker's sequence (§6) that runs alongside rule evaluation rather than replacing it (in the same loop that already merges rule observations and cbs_features.observe_loan()'s loan-conduct scores), reading the active model version the same way the worker already reads the active rule catalogue (rules.active_model(), mirroring active_rules() and policy()'s own cached-fetch shape).

Runtime — AD-14, as decided. In-process inside analytics-service, not a separate scoring service behind AD-08's internal-API pattern: scoring needs the same account context features.load_context already builds per batch, and a second process would mean either duplicating that computation or paying a network hop per transaction for every scored row — the same reasoning AD-09 already applies to keeping analytics-service one service. CPU-only, an sklearn.ensemble.IsolationForest over five tabular features (velocity, counterparty, outflow-ratio, small-credit and structuring signals already computed for VEL-01/LAY-01/LAY-02/VEL-03/SME-01); Python + FastAPI (AD-01) already carries the dependencies this needs, no GPU or separate model-serving stack. services/analytics_service/app/detection/model_scoring.py.

Calibration, not a guessed constant. score_samples is lower-is-more-abnormal with no fixed range; scoring the mid-point of a real tenant's own traffic against a hand-picked transform put the bulk of ordinary traffic above any sane threshold during development. The trained artifact instead carries its own training set's 1st/99th-percentile score bounds, and model_scoring.score() rescales linearly against them, clamped to [0,1] — a live transaction outside the training range becomes a boundary value, not a value outside the catalogue's own scale.

Built: the model config body's model_artifact slot (format, object-storage uri, sha256) sits alongside challenger_evaluation and the committee attestation, validated by the same route (config_service/app/model_artifact.py) at proposal time — refused before pending_activation, the same discipline the other two gates already had. Only sklearn-joblib is a supported format; onnx is named as a future option and explicitly refused, not silently accepted and left to fail unexplained at scoring time. Only file:// URIs are implemented today — object storage (s3://, azure blob) is where a real deployment's artifacts belong, not built because nothing in this environment has that infrastructure to point at. A batch loads the artifact once (cached by URI+sha256, so a replacement file is loaded fresh rather than silently reusing a stale one) and verifies its digest before every deserialisation, refusing a mutated or truncated file rather than scoring with something nobody approved. See scripts/train_velocity_anomaly_model.py for how a version is actually produced — an unsupervised IsolationForest fit against whatever history a tenant already has, since no tenant has labelled fraud outcomes to train against yet. This is a first working fit, not a validated model — detection quality against real fraud outcomes is unmeasured until BR-806's backtesting harness runs against live traffic, which this phase does not claim to have done.

Phase 3 — GNN-based fraud-ring detection Built

The account graph GET /analytics/{tid}/graph already computes (built for the Investigator/Account 360/AML network-graph view) was the natural training input — no new data model, a new consumer of data that already existed, within one tenant's own graph. Training needs the tenant's whole transaction graph, not the case- or account-scoped neighbourhood the live endpoint returns for display (or its unscoped "busiest structure" fallback, itself limited to already-LAY-flagged traffic) — built as its own query variant, graph_model.build_tenant_graph(), not a new data source. Resolved by OD-07: this phase did not wait on a cross-tenant data-sharing decision, because it did not need one — the isolation decisions this platform had already made (AD-03: schema-per-service in one instance; the multi-tenancy model in §9: no cross-tenant queries, enforced at the database role) are simply unaffected by training a model on data one tenant already owns.

Task and model. No ring labels exist to train against, same situation Phase 2 was in — so this is self-supervised, not classification: a 2-layer GraphSAGE (graph_model.RingScoreEncoder; inductive, deliberately not a transductive GCN — an account graph gains new nodes constantly, and an inductive model scores one it has never seen without retraining) produces a node embedding per account, seeded with Phase 2's own five features plus three the GNN specifically needed and Phase 2 never did — log-degree and log in/out-flow, since a model with no signal about neighbourhood size or flow cannot use its own aggregation for anything. Trained on link prediction (a real edge's endpoints should dot-product higher than a random pair's, via negative sampling) — a standard, label-free way to make an embedding space reflect graph structure. Those embeddings are then scored for anomalousness by the same calibrated-percentile pipeline Phase 2 built (model_scoring.load()/score()), extended (not replaced) to reconstruct the encoder from the bundle first — an embedding is just a richer feature vector to the scoring half, so that code needed no new logic, only a new upstream feature computation. Surfaced as LAY-05 (fraud-ring membership) — the layering/mule family, not VEL, since this is topology, not velocity.

Runtime — does not reuse AD-14's placement, by design. A GraphSAGE forward pass over a whole tenant graph is not a per-transaction operation the way Phase 2's five-feature IsolationForest call is; recomputing embeddings for the whole graph on every batch the detection worker claims would make every batch as slow as a full retrain. This phase runs as a periodic scheduled script instead (scripts/refresh_ring_scores.py, the same shape scripts/run_subscriptions.py --once and scripts/run_retention.py already are, driven by cron/Task Scheduler, not a new microservice — AD-06's reasoning: batch, not stream) that refreshes analytics.account_ring_score (tenant, account, score, model version, computed at; upserted, one row per account) on whatever cadence an operator schedules it at. The detection worker's per-transaction loop does a cheap primary-key lookup against that table for LAY-05, the same shape device_clusters()'s per-batch dict-return already has for LAY-04 — never a live GNN forward pass in the payment path. An account absent from the table (new since the last refresh, or the refresh has never run) contributes nothing to that transaction's observations — correctly not the same as a confirmed-typical score of zero, and not the same failure as no model existing at all: the coverage report distinguishes "no active graph-ring-score model for this tenant" (LAY-05 genuinely unmeasurable) from "this specific account has no score yet" (silently absent from one transaction's observations, exactly like an unprofiled account's CHN-03).

Dependency, recorded separately — AD-15. PyTorch + PyTorch Geometric (CPU-only) is a materially heavier dependency than AD-14's scikit-learn/joblib/numpy (torch's own CPU wheel is ~125MB) — deliberately not folded into AD-14's "no GPU, no separate model-serving stack" framing, since Phase 2's choice does not carry over just because both phases are ML, exactly what AD-14 itself said Phase 3 should not assume. The compiled-extension risk flagged when this was scoped (torch-scatter/torch-sparse, historically the fragile half of a PyG install) did not materialise: PyG 2.8's pure-PyTorch message-passing fallback covers SAGEConv without either, verified with a real install and a real forward pass on this deployment's own target platform before the rest of this phase was built.

The prerequisite this phase exposed is fixed, not merely documented. Phase 2's /internal/model/{tid} and rules.active_model() used to return the tenant's first active model-kind row, full stop — correct only while exactly one model existed. Both are now /internal/model/{tid}/{name} and rules.active_model(tenant_id, name), keyed by the config's own name (read from features.NEEDS_MODEL, never retyped as a literal at a call site) — the config data model already supported two same-kind, differently-named active versions (ConfigRepository.activate() archives a sibling by tenant+kind+name, not tenant+kind alone); only the query layer had never been asked to distinguish them. velocity-anomaly (VEL-04) and graph-ring-score (LAY-05) are now active independently per tenant, each reachable only by its own name — verified by a test that activates one and confirms the other's name still reports unavailable.

Phase 3b — Federated learning (deferred)

Decoupled from Phase 3 by OD-07. Federated learning's entire premise is training across a data boundary wider than one tenant — training within one tenant's own data is not federation, it is centralised training with an extra network hop, since there is only one data holder. That wider boundary is a materially different posture than anything AD-03 or §9's isolation model contemplates, and this document does not carry a design for it: no architecture is specified here because none is owed until a specific multi-bank engagement creates both the demand and the consent basis for it. §13 (identity and access) and §9's isolation model are unaffected in the meantime — there is nothing to build against them.

Phase 4 — Explainable-AI dashboards & regulator-ready reporting

No new service. Extends analytics-service's existing model-inventory and override-log endpoints (§12) with a per-alert rule-vs-model attribution field, and reuses the scheduled-distribution machinery already built for board packs (§7b, BR-507) to add an explainability appendix. Reporting only; there is no new data to protect or reconcile that §8's sixteen invariants don't already cover, since this phase reports on Phase 2/3's outputs rather than producing its own facts.

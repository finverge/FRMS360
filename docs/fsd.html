How this document was built

Every use case below traces to a business requirement in the BRD and to the running code — the actor's role name, the roles permitted on a state transition, the endpoint a step calls, the status values a record can hold. Where a capability exists only as a roadmap item, the use case says so and is marked Pending rather than described as present. Nothing here is aspirational unless labelled as such.

Purpose, scope & how to read this

The BRD says what the platform must do and why. The HLD says how it is built. This document says who triggers each piece of behaviour, from which screen or interface, in what order, and what the system guarantees them in return.

It is organised by actor, not by module, because that is how the people who will sign off on this platform read it: a Principal Officer wants to see everything they can do in one place, not their filing use cases in §9 and their alert use cases scattered through detection. Each of the eleven human personas gets its own section: a one-line summary, a use-case diagram scoped to that actor, a complete table of their use cases, and a small number of fully detailed specifications for the ones that carry the most procedural weight — a natural-justice hearing, a maker-checker fraud declaration, a filing acknowledgement.

Four system actors are specified alongside the human ones — a payment switch or CBS extract job, the bank's identity provider, the regulators who receive a filing, and law enforcement — because a functional specification that only describes what a person can click is missing half of what the platform does. §17 covers them.

Notation used throughout

  • UC-XXX-nn — a use-case identifier, prefixed by actor code (see the persona table in §3). Referenced from the traceability matrix in §19 and, where relevant, from other use cases via includes — a step that is itself specified in full somewhere else, rather than repeated.
  • BR-nnn — the business requirement in BRD v1.7 that this use case satisfies. A use case with no BR reference is either purely a screen convenience or a system-actor interface documented for completeness.
  • Built / Partial / Pending — carried over unchanged from the BRD's own status column. A pending use case is written in the future tense; everything else describes what the running code does today, proven by the test named where it matters.

System overview

One paragraph, because the HLD already owns this ground in full.

Fraud360 is a multi-tenant fraud risk management and early-warning-signals platform for Indian banks, co-operative banks and NBFCs. It ingests payments across five rails (UPI, IMPS, NEFT, RTGS, card) and non-payment signals from the core banking system, scores them against each tenant's own board-approved catalogue of indicators, and carries a signal that fires all the way through to a defensible regulatory filing. Two detection lanes exist side by side: an inline lane that returns a go/no-go answer inside the payment window for the rails a tenant configures for it, and a near-real-time lane that scores the full catalogue, including typologies that cannot be known at the moment of authorisation, and raises alerts that a human works. Eleven roles see eleven different slices of the same underlying facts, enforced server-side rather than by hiding a tab in the console.

What follows takes that system as given and asks, screen by screen and interface by interface: who is allowed to do what, and what happens when they do.

Cross-cutting specifications

Three use cases sit underneath nearly everything else in this document. Specified once here, and referenced as includes from every persona section rather than repeated eleven times.

UC-AUTH-01

Sign in with a second factor

Actor
Every human persona
Trigger
The user submits an email and password on the console login screen, or arrives via the bank's SSO link
Preconditions
The user has an active account for a tenant that is not suspended or offboarded
Main flow
  1. User submits email and password, or is redirected from the bank's OIDC or SAML 2.0 identity provider (discovery is by organisation short name, so the user never has to know which protocol their bank uses)
  2. The system verifies the credential and issues an mfa_pending token — not a usable session
  3. User supplies a TOTP code, or a single-use backup code as fallback
  4. The system verifies the code and issues a full session: an access token valid 30 minutes, and a refresh token
  5. The refresh token is honoured up to 4 hours of inactivity, or 7 days absolute, whichever comes first
Alternate flows
  • First login — the user is forced to set a permanent password and enrol a second factor (QR code, confirmed by one live code) before a session is issued. An enrolment that is never confirmed leaves the account without a usable second factor and the login refused, rather than silently weaker
  • Federated sign-on — the identity provider's signed assertion is read only from the element the signature actually covers (defends against signature wrapping), and the assertion ID is recorded so it cannot be replayed
Exception flows
  • 5 consecutive failures on the password or the TOTP code lock the account for 15 minutes
  • A tenant that is suspended or offboarded refuses every login, with the reason — see UC-TEN-01
Postconditions
A session exists, scoped to the user's role and tenant; every subsequent action is attributed to it
Business rules
BR-706, BR-707, BR-708, BR-709, BR-710
UC-M2M-01

Authenticate a bank system as a machine

Actor
Payment switch, CBS extract job, ETL pipeline (system actor, §17)
Trigger
The system needs to submit transactions or request an inline decision, and holds no valid token
Preconditions
A Tenant Administrator has issued a credential scoped ingest, decide, or both — never full access
Main flow
  1. The system exchanges its client ID and secret for a bearer token via the OAuth2 client-credentials grant — no MFA, and none bypassed, because this credential class has no interactive login path to bypass
  2. The token carries the credential's scope and a short expiry
  3. Every subsequent call presents the token; the standard principal check refuses machine tokens by default, so an endpoint must opt in to accept one
Exception flows
  • An expired, revoked, IP-disallowed or certificate-mismatched credential is refused with the specific reason, not a generic error
  • A token scoped ingest cannot request a decision, and vice versa
  • The tenant's own lifecycle status is checked on every token issuance and, for the decision path, cached and re-checked every 15 seconds — a suspended tenant's switch stops within that window, not only its human users (see UC-TEN-01)
Postconditions
A scoped, time-limited token; every issuance and refusal is audited, since a refusal is often the more interesting record for an investigation

Lane A — inline decisioning

Answers allow or decline (UPI, IMPS) or additionally challenge (Card) inside the payment window, on a per-rail latency budget the tenant sets. NEFT and RTGS are routed to Lane B by default — they settle in a window wide enough that scoring with full context finds more than an 80 ms check ever could.

Reaching Lane A over ISO 8583, not only JSON (BR-317, Partial)

The /decide contract above is JSON. Some card/EFT switches have no practical way to originate a JSON call — asking every such vendor to build a translation layer of their own does not scale. A second front door, iso8583_gateway, decodes an ISO 8583 authorisation message (the standard public data elements — PAN, amount, transmission time, STAN/RRN, terminal and merchant ids) and calls the same /decide contract as any JSON integrator would: same rule catalogue, same policy, same decision log. It is a protocol adapter in front of the one decision engine, not a second one. Core codec, field mapping and connection handling are built and unit-tested; it is not yet deployed for any tenant. Every switch vendor's private data elements and exact response-code table differ, so field mapping is confirmed against a named pilot vendor's own spec before go-live, and whether Fraud360 terminating a raw PAN brings it into PCI-DSS scope is a compliance decision still open. See docs/ISO8583_LANE_A_SCOPING.md.

Entity-type gating (BR-111)

The 12 rules marked "B only" above and named in the table — BEH-02/03, CPT-03, CBS-01/02/03, QUAL-01/02/03, LOS-01/02/03 — share one property none of the other 19 do: their premise is a lending relationship (a borrowal account, pledged collateral, a disbursement, a "primary banker", or — for LOS — an application for one). Checked against the actual Chapter III EWS text of all nine RBI 2026 Directions, every entity type carries that borrower/financial-performance language except Payments Bank — a PB licence cannot extend credit, and its Direction (RBI/DoS/2026-27/430) has no credit-related EWS section at all. For a Payments Bank tenant, none of these 12 are seeded at onboarding; the platform starts that tenant on 19 rules, not 31, and detection never evaluates the excluded 12 because they are absent from the tenant's active configuration, not merely deactivated.

TBM-01/02/03 (trade-based: merchanting trade, Letters of Credit, foreign bills) were checked the same way and left ungated on purpose. None of the nine 2026 Directions tie trade-finance authorisation to entity type — that vocabulary traces to RBI's older 2016 EWS circular, not the current Directions — and Authorised Dealer (forex) status is issued to an institution separately from its entity-type licence. Gating TBM by entity_type would encode a guess as if it were a verified fact; it is recorded as a roadmap item pending a per-tenant AD-licence signal the platform does not yet capture, not built now.

Deep dive: The 9 Lane A signals and how they work

Each Lane A rule detects a specific fraud pattern using account counters available at authorization time. Here is what each one catches, in language for a risk conversation.

VEL-01 · Value velocity against baseline

What it catches: A single transaction that is dramatically larger than the account's own historical pattern.

Real example: A customer who normally sends ₹5,000–₹15,000 per month suddenly initiates a ₹200,000 transfer. This 13× spike against their 30-day baseline triggers an alert.

How it works: Fraud360 maintains a rolling 30-day average for each account and flags any single payment that exceeds a configurable multiple (often 5–10×). Legitimate spike? The customer can be challenged or the rule threshold adjusted per-tenant. A mule? The pattern fits.

VEL-03 · Small-credit frequency spike

What it catches: A sudden explosion of micro-transactions below a threshold, often used to evade detection or test compromised accounts.

Real example: An account that has never transferred more than twice per day suddenly initiates 15 transfers of ₹9,999 each within a single hour.

How it works: Counts the rolling number of small transfers (below a configurable amount like ₹10,000) in a time window. Structuring fraudsters often use precisely this tactic to stay under AML thresholds while moving large sums.

SME-01 · Sub-CTR structuring count

What it catches: Multiple transfers just below the Currency Transaction Report (CTR) filing threshold (₹10 lakh), a classic structuring pattern.

Real example: A borrower makes seven separate transfers of ₹9.99 lakh on the same day, totalling ₹69.93 lakh. This is textbook structuring to evade regulatory reporting.

How it works: Counts transactions in a rolling window that fall just below the CTR threshold and flags when the count crosses a limit (typically 3–5 in 24h). The platform knows the exact CTR threshold for your jurisdiction.

SME-02 · PIN-less UPI structuring

What it catches: Rapid-fire micro-UPI transfers (below the PIN-less limit) that collectively move a large amount without individual authentication.

Real example: A compromised phone sends 20 UPI transactions of ₹5,000 each to different beneficiaries within 10 minutes—totalling ₹1 lakh drained from the account without a PIN being entered for each transfer (many banks allow PIN-less UPI up to ₹5,000).

How it works: Tracks the count and volume of UPI transfers below the PIN-less limit in a rolling window. A spike indicates either account compromise or deliberate low-value-transfer fraud.

LAY-01 · Outflow drain (layering)

What it catches: Nearly all money flowing into an account is immediately funnelled out—the hallmark of a money mule or money-laundering layering account.

Real example: An account receives ₹10 lakh over a week and within 3 days sends out ₹9.8 lakh to 12 different beneficiaries. The outflow ratio is 98%—far above the normal 40% for this account type.

How it works: Compares outbound transaction volume to inbound volume in a rolling window (typically 7 days). A ratio above a threshold (often 80–90%) flags the account. Legitimate fast-flowing accounts (traders, e-commerce sellers) can be whitelisted at the tenant's discretion.

LAY-02 · Fan-in/fan-out hub (distinct counterparties)

What it catches: An account with an abnormally high number of unique transacting partners—often a sign of a money-collection or distribution hub.

Real example: A new account interacts with 47 different beneficiaries in a single week, whereas the average account at this bank interacts with 3–4. Money is flowing in from some and out to others in rapid succession.

How it works: Counts distinct counterparties (unique beneficiary accounts) in a rolling window and compares to the account's own baseline or a peer baseline. A sudden spike to 40+ unique payees raises an alert. Legitimate high-volume merchants can be configured with higher thresholds.

LAY-04 · Device fingerprint clustering

What it catches: Multiple accounts being accessed from the same device fingerprint (MAC address, device ID, etc.), suggesting fraud orchestration or account takeover of multiple customer accounts.

Real example: A compromised phone accesses 8 different customer accounts within 30 minutes, each initiating a transfer. The device fingerprint is the same for all 8.

How it works: Maps device fingerprints to account numbers and counts the number of accounts accessed from a single fingerprint. A sharp rise (e.g., from 1 account to 5 accounts) indicates either fraud or a shared-device scenario (family phone). Tenant policy decides the threshold.

BEH-01 · Dormancy on large payment

What it catches: An account that has been inactive suddenly makes a high-value payment—often the account has been dormant for months and an attacker has just compromised it.

Real example: A salaried customer's account has seen no transactions for 8 months, then suddenly initiates a ₹50,000 transfer. The account's baseline suggests this customer is on extended leave or the account is dormant—a sudden large transfer is suspicious.

How it works: Measures the time gap since the account's last transaction and flags if a high-value payment (above a configurable threshold) arrives after an extended dormancy period. Automated reactivation of old accounts often triggers this.

CHN-01 · New device + new payee + high value

What it catches: A payment from an unfamiliar device to a unfamiliar beneficiary, in a large amount—the classic account-takeover signature.

Real example: A customer's phone is stolen and used immediately to send ₹30,000 to a new account never seen before. The system sees three red flags at once: device is new, payee is new, amount is high.

How it works: The channel (mobile app or bank branch) supplies this observation directly to Lane A (it's not computed here). The "risk_signals" count combines device newness, payee newness, and value size. A combined score above a threshold (typically 2–3 simultaneous factors) triggers a decline or challenge.

Why these 9 work inline and others don't

All nine Lane A rules rely on either (1) precomputed per-account counters that are updated on every transaction, or (2) information the channel already has. No external lookup, no missing data, no waiting for the settlement window. The other 19 rules need either a feed not yet connected (sanctions lists, trade records), a fact that only emerges after settlement (CBS repayment data), or a signal that cannot exist yet (a beneficiary's age, if you have never seen that pair before). Those rules do not belong in a 50–150 ms decision window; they belong in Lane B, where the full account and network context is available.

Deep dive: The 19 Lane B–only signals

These 19 rules run only in Lane B (near-real-time, p99 2.65 seconds after settlement). They either need external data, post-settlement facts, or signals that only form over time.

CPT-01 · Beneficiary age (new payee)

Why it's Lane B only: Requires a set store (first-seen timestamp for each payee pair), not an account counter. If derived from counters alone, an unknown payee would always read as age zero and fire on every large payment—a false positive generator, not a control.

What it catches: Payments to a beneficiary added to the account for the first time, especially in a large amount. Legitimate? Maybe. Suspicious? Depends on the account.

Example: A customer adds a new payee and immediately sends ₹2 lakh. Lane B has the full history and can assess whether the account routinely adds and uses new payees or whether this is out of pattern.

VEL-02 · Beneficiary-pair age velocity

Why it's Lane B only: Same issue as CPT-01—relies on first-seen-pair data that cannot be reconstructed from counters without false alarms.

What it catches: A sudden jump in value to a very new payee pair.

CPT-02 · Sanctions / PEP / Central Fraud Registry screening

Why it's Lane B only: Sanctions, PEP (Politically Exposed Person) and CFR (BR-509) lists are not loaded in the payment authorization path; they are too large and update too frequently. They are queried asynchronously after settlement.

What it catches: Transactions to or from sanctioned individuals, entities, PEPs without prior disclosures, or parties already reported as fraud elsewhere in the banking system via RBI's Central Fraud Registry.

Example: A payment arrives from an account to an entity later identified as OFAC-listed. The transaction proceeds but an alert is raised in Lane B for investigation and possible reversal.

On CFR specifically: unlike a sanctions list, RBI does not publish CFR as a bulk feed — a bank's users hold individual portal credentials for case-by-case lookups (Directions, Chapter VI-B). The Directions' own definition (para 4(1)) is that CFR is populated from a bank's own FMR filings, not a return the bank files separately — so there is no second filing to build here, only the screening side: a tenant's compliance team loads what its portal lookups found through the same reference-data console every other list uses, honestly unloaded — not silently clean — until they do.

CPT-03 · CERSAI charge registry

Why it's Lane B only: CERSAI (Central Registry of Securitisation Asset Reconstruction and Security Interest) lookups are external registry calls, not real-time.

What it catches: Transactions from accounts with undisclosed charges, liens, or pledged collateral flagged by CERSAI.

LAY-03 · Circular/multi-hop money flow

Why it's Lane B only: Requires a graph traversal across multiple transactions to detect cycles (A → B → C → A). The cycle has not closed at the moment of A's payment; Lane B detects it only after B and C settle.

What it catches: Money laundering "round-tripping" where funds move in circles to obscure origin and create false transaction records.

Example: Funds flow from Account A to B (detected), then B to C, then C back to A. Lane B's post-settlement analysis spots the cycle.

CHN-02 · Geolocation anomaly

Why it's Lane B only: Geolocation feeds are not contracted in-path and must be queried post-settlement.

What it catches: A payment from a device whose geolocation is inconsistent with the account's known geography or profile.

Example: An account normally operates in Mumbai but a high-value payment originates from a device located in a high-crime territory or a country on a watch list.

CHN-03 · Off-hours activity

Why it's Lane B only: Requires the account's hourly activity profile, which is computed post-settlement and not exposed as a real-time counter.

What it catches: Transactions at hours when the account holder never normally transacts (e.g., 3 AM for an account that always transacts 9–5 AM).

SME-03 · Invoice-level trade structuring

Why it's Lane B only: Requires invoice-level data from supply-chain or trade systems—not available at authorization.

What it catches: Over-invoicing or invoice manipulation in trade flows to move money disguised as legitimate commerce.

BEH-02 · Repayment source mismatch

Why it's Lane B only: Requires CBS repayment data, posted after settlement. The repayment funding source is not known until settlement clears.

What it catches: A loan repayment arriving from an unexpected source (not the original borrower, not a known guarantor)—may indicate account takeover or fraud.

Example: A borrower's loan repayment arrives from a third-party account that was never listed as authorized to repay—suspicious and potentially a misapplied payment.

BEH-03 · End-use deviation

Why it's Lane B only: Requires tracing money across subsequent transactions to confirm it reached its stated end use. Only visible after multiple settlement cycles.

What it catches: Loan funds disbursed for one purpose being diverted to another use—either fraud or violation of loan covenants.

Example: A working-capital loan is disbursed for inventory purchase, but the funds immediately flow into a real-estate investment account. Lane B flags the deviation.

CBS-01 · Disbursal-to-withdrawal deviation

Why it's Lane B only: Requires loan account history from the CBS (Core Banking System), available post-settlement.

What it catches: A loan disbursed but immediately withdrawn/repaid or moved out before the borrower had time to deploy it—often a sign of layering or loan fraud.

CBS-02 · Collateral and security inconsistency

Why it's Lane B only: Requires stock audit reports and security records from the CBS—not real-time feeds.

What it catches: Transactions from loan accounts where the pledged collateral appears to be missing, sold, or transferred without disclosure.

CBS-03 · Sale proceeds misrouting

Why it's Lane B only: Sale proceeds are only known after the asset-sale transaction settles and is recorded in the CBS.

What it catches: Proceeds from an asset sale being routed to unauthorized accounts instead of loan repayment or the borrower's specified account.

TBM-01, TBM-02, TBM-03 · Trade-based money laundering

Why they're Lane B only: Require trade-finance records (LC details, bills of lading, invoices) and the foreign-bills register—all external to the payment system.

What they catch: Over/under-invoicing, double-invoicing, phantom shipments, and other classic trade-finance fraud schemes.

Example: An import LC shows ₹10 lakh for goods, but the invoice is ₹5 lakh—over-invoicing by 100% to move money across borders in disguise.

QUAL-01, QUAL-02, QUAL-03 · Qualitative credit indicators

Why they're Lane B only: Entered manually by the credit-monitoring team after review of account behavior and external data (media reports, customer complaints, regulatory notices).

What they catch: Red flags identified through human review: adverse media mentions, management concerns, sudden behavioral changes, etc.

Example: The credit team notes that a borrower has appeared in adverse media (alleged involvement in litigation, regulatory penalty, or reputational event). This feeds into the qualitative score in Lane B.

Summary: Why the split works

Lane A (9 rules): Detects the most urgent fraud signatures using only data that exists at authorization time—account counters and channel-supplied signals. Answer in 50–150 milliseconds.

Lane B (31 rules for a lending-capable entity type): Adds 22 more rules that need external feeds, post-settlement facts, or signals that only form after the payment clears — or, for the three loan-origination rules (BR-214), before it. Answer in ~2.65 seconds, but with full context. Includes all of Lane A's signals, so no coverage is lost—only timing. A Payments Bank tenant runs 19 in Lane B, not 31 — the 12 credit-linked rules are never seeded for a licence that cannot extend credit (BR-111, see the entity-type gating note above).

Result: A bank that runs only Lane A gets 9 out of its entity type's catalogue in real time and loses nothing—the 9 catch the highest-confidence attacks and are unaffected by entity-type gating. A bank that runs both gets its full catalogue: 9 at authorization time, the rest after settlement. A bank that runs only Lane B gets the full catalogue but waits 2–3 seconds.

The boundary is not speed

Three of the twenty-two deferred rules — LAY-03, CPT-01, VEL-02 — are excluded for a reason no amount of engineering removes: the signal has not formed yet at authorisation time. A fan-in hub is invisible until the fan has formed; a beneficiary read from a context with no first-seen-pair set would compute as age zero and fire on every high-value payment, which is a broken control, not a fast one. The other nineteen are deferred because a feed is not yet connected or a fact only exists after settlement — connecting them moves rules from Lane B's "unmeasured" state to scored, not from Lane B to Lane A.

UC-TAD-07

Create, edit and delete a role

Actor
Any role holding can_admin_tenant — checked dynamically, so a custom role the tenant has granted admin scope to can manage further roles itself, not only the seeded tenant_admin
Trigger
The fixed ten roles do not match the bank's own org structure — a title, a narrower grant, or a role scoped to one region or desk
Main flow

Business rules
BR-113
BR-113's capability check now runs platform-wide, three flags deep

A tenant's roles are real, editable, per-tenant database rows — the write path, the platform-only guardrails, the maker-checker elevation and the full audit snapshot on every change are all built (phase 2b). A custom role is functional within tenant-service's own admin surface, assignable to a user via BR-108, and — phase 2c — recognised by analytics-service, config-service, decision-service and notification-service too, through cp_common.dynamic_roles: a shared module every one of them imports, fetching a tenant's custom-role catalogue from tenant-service's GET /tenants/internal/{tenant_id}/roles and caching it against the same generation-token mechanism config-service's rule/policy changes already use, so an edit is visible everywhere the instant it is made, not after some clock interval. Every one of the ten fixed roles still resolves with zero network calls — nothing about existing behaviour changed for them. ingestion-service needed no change at all: BR-213 machine credentials carry scopes, not human roles.

Phase 2d closed the sharpest remaining gap: config-service's maker_checker.ELIGIBLE_ROLES used to be a hardcoded name list mixing risk_manager in alongside the two admin-capable roles, because TenantRole had no flag for "may activate configuration" on its own. It has one now — can_activate_config, checked dynamically the same way as the other two — so ensure_eligible() is one capability check instead of a name comparison plus a fallback, and a custom role can be granted exactly the risk_manager-equivalent capability, independent of can_admin_tenant. Raising it is staged through the same elevation confirmation as the other two flags; a bank does not get to hand out configuration authority any more casually than it hands out admin scope. What remains open is narrower still: a small number of call sites (analytics-service's FILING_ROLES/CTR_ROLES) mix in roles like principal_officer that no flag on this platform describes at all — extending those means new capability flags, real and separately-scoped, not attempted here. Recorded rather than left implicit, in the same spirit as the BR-108 invite-flow finding above.

  5. A batch is accepted partially: each rejected row is reported with its index and reason, and the rest are retained — the caller learns exactly which three of forty thousand rows failed, not that the whole file did
  6. The inbound payload is retained immutably, separate from anything derived from it, with the time of receipt — so "we sent you 40,000 rows and you booked 39,997" is answerable with the three rows, not a count
Postconditions
Accepted rows enter the near-real-time detection lane; queue depth, provenance and freshness are exposed for operational monitoring (UC-PAD-04)

Main flow
  1. Switch calls the decision endpoint with the payment and whatever signals the channel already knows — new device, new beneficiary

Open items & assumptions

What a reader should not take for granted from the rest of this document — findings from writing it, and constraints inherited from the BRD.

Findings from specifying against the running code

  • User invitation is now a Tenant Administrator action. POST /tenants/{id}/users, and the update/remove routes beside it, are guarded by require_capability("can_admin_tenant") — checked dynamically against the tenant's own role catalogue (BR-113), not require_role("platform_admin"). A guard against leaving a tenant with zero admin-capable users (_sole_admin_guard) applies to every reassignment and removal. This was previously platform-only; it no longer is. See §15.
  • SSO / IdP configuration now has a console UI. A Tenant Administrator can create, edit and delete their own OIDC/SAML providers, with role-mapping validated against the tenant's own assignable roles and the client secret write-only. UC-TAD-03 is now marked Built in §20.
  • Self-service tenant onboarding (BR-109) is now built as its own unauthenticated path (POST /tenants/self-service, UC-PAD-01b) rather than as an extension of user invitation — the two were previously conflated in this document. A prospective bank provisions a fully working sandbox tenant with no platform_admin action of any kind; isolation is enforced by refusing source="live" traffic from a sandbox tenant at the ingestion endpoints themselves, not left to self-reporting. Promotion out of sandbox (UC-PAD-03b) remains a deliberate platform_admin action.
  • A tenant's FRM policy — including its PMLA Principal Officer — now has a console and API path too. ConfigCreate.kind validated against rule|typology|network_map only, refusing policy at the request schema — not merely a missing editor. That is fixed: a tenant admin can create and activate a policy version from the console, including the Principal Officer field mandatory on every STR (see §10 UC-PO-02), still gated by the same board-attestation requirement on activation as before.
  • Branding and machine-credential administration are tenant-scoped, not role-restricted. The server checks resolve_tenant_scope on these endpoints — any role scoped to the tenant may call them — rather than a specific role name. The console only exposes them to Tenant Administrator, so this is a defence-in-depth gap rather than a live exposure, and is noted for completeness rather than urgency.
  • Maker-checker now extends to privileged configuration changes, not only fraud declaration. Activating a rule, policy or model config version passes through pending_activation: a second, different eligible person must confirm before it reaches live decisioning, and the proposer may not also be the confirmer (BR-715, UC-FRM-03). Closes the item previously carried forward as open below.
  • Champion/challenger evaluation, committee approval, and a loadable artifact reference before a model configuration is promoted are now built — and a model now genuinely scores real traffic. A new model config kind may not even be proposed for activation without a recorded evaluation (BR-807), Model Risk Management Committee sign-off (BR-808), and a verified model_artifact reference (AI/ML roadmap Phase 2, HLD AD-14) — see UC-MDL-04. Once activated, analytics-service's detection worker loads that artifact and scores VEL-04 in the same batch every other rule scores in (§23). This was previously a governance floor built ahead of any model existing; it no longer is, for Phase 2 specifically — Phases 3 and 4 (AI/ML roadmap, OD-06) still have no live scoring.
  • RBI's Central Fraud Registry (CFR) needed no second filing. The Directions define CFR as populated automatically from FMR submissions (already built); the bank's own obligation is to screen against it. CFR is now a reference-data source alongside sanctions/PEP/negative-list, feeding CPT-02 (BR-509) — honestly unloaded, since RBI grants CFR access as per-user portal credentials rather than a bulk feed a schedule can poll.

Carried forward from the BRD

  • FMR and STR artefacts are assembled, validated, hashed and retained in the platform's own structured form; binding to RBI's and FIU-IND's own prescribed submission formats is a compliance decision pending OD-04, not engineering work (UC-PO-02).
  • Right-to-audit evidence pack, documented disaster recovery with a stated RPO/RTO, and capacity evidence beyond a single worker are all Pending (BR-908, BR-909, BR-910) — see the BRD's own release-gate table for what each blocks.

Assumptions this document inherits from the BRD

  • Each tenant can expose transaction data by API or file within minutes of settlement, and federates identity from an existing IdP rather than managing users in the platform long-term.
  • Each tenant's board approves its own thresholds; the vendor supplies defaults, never advice — reflected throughout §6–§16 as "board-approved", never as a platform constant.
  • Reference data (sanctions, CERSAI, CBS extracts) is licensed or supplied by the tenant, not by the platform.

AI/ML roadmap

What each persona actually sees change, phase by phase. Committed scope per the BRD's AI/ML roadmap (OD-06); no remaining phase has a committed delivery date, and each depends on the one before it landing first. Phase 2 has now landed - see its own heading below for what actually changed, not just what was planned.

Phase 1 — Device & behavioural biometrics

No new screen. The Fraud Analyst's evidence drawer (§6, "why this fired") gains new CHN-family reason codes sourced from device-posture and behavioural-biometric features — typing cadence, touch pressure, session/gesture patterns — alongside the device id already shown there. The EWS Signals dashboard's by-family breakdown starts reporting volume under these new CHN sub-rules. Signal capture and matching are not specified here — they are VideoPD's and the Human Fraud Detection Framework's functional domain; this platform consumes their output as a feature, not a capability it implements itself.

Phase 2 — Transaction velocity & anomaly-detection models Built

No new screen. This is the first phase where the Model Risk / Data Science persona's existing UC-MDL-01…04 (§13) stop being exercised against an empty inventory: a real model config version is proposed, evaluated, committee-approved and now also artifact-verified (AD-14) through the same console flow already built, and the Analyst's alerts genuinely carry a model-scored indicator (VEL-04) alongside the rule-scored VEL family. The Fraud Analyst cannot yet tell which alerts came from which — that distinction is Phase 4's job.

Phase 3 — GNN-based fraud-ring detection Built

The Investigator, Account 360 and AML dashboards' existing network-graph view (already rendering the account graph for visual link analysis) is joined by a new alert indicator, LAY-05, alongside the existing layering/mule family in the Analyst's and Investigator's evidence drawer, with its own "why this fired" trace like every other alert (BR-805) — a direct answer to the Senior Investigator's "is this one mule, or a ring?" question (§7) instead of an inference from edge density alone. Resolved by BRD OD-07: this runs within one tenant's own graph, no cross-tenant data-sharing decision needed.

One visible difference from every other indicator: LAY-05's score refreshes on whatever schedule an operator runs scripts/refresh_ring_scores.py on (per HLD §16), not per transaction the way VEL-04 (Phase 2) or the rule-based indicators do — a graph model is too expensive to recompute for every batch. An Investigator opening a very recent case may see LAY-05 absent rather than stale on a brand-new account the last refresh never saw; the account_ring_score row's own computed_at is available to show when a present score was last produced, not just what it is.

Phase 3b — Federated learning Deferred

Decoupled from Phase 3 by BRD OD-07: aggregating model updates across tenants/banks is not commercially triggered by any engagement in front of it, and no screen is specified here because none is owed until one exists.

Phase 4 — Explainable-AI dashboards & regulator-ready reporting

The Model Risk dashboard gains a per-alert explainability panel distinguishing a rule-scored decision from a model-scored one, and the scheduled board pack (already built, BR-507) gains an explainability appendix for the RBI Inspection persona — the same "prove why this account was flagged" question §14 already asks of the rules engine, extended to cover Phase 2 and 3's models. Not independently specifiable: there is nothing to explain or report on until those phases produce a model to describe.
